# Feature: pagination-contracts

Unify list pagination contracts between el-rodeo-api and el-rodeo-web: keyset-cursor pagination for animals/purchases/payments, offset/limit kept for users/supplies, filtered totals surfaced in the UI, and dedicated unpaginated `/params` reference endpoints for form dropdowns.

- Branches: both repos branch from `main` as `feat/pagination-contracts` before first source write.
- Delivery strategy: `feature-branch-chain` (chosen 2026-11-01 via ask-on-risk; commits accumulate on `feat/pagination-contracts` in both repos; slice boundaries and PR membership recorded here as units commit; push stays user-ordered).
- Test runners: API `TRUSTED_HOSTS='["*","test","localhost"]' uv run python -m pytest <test>` (from el-rodeo-api; PG 5432 + Redis 6380 up). Web `npm run build` (tsc -b && vite) + `npm run lint` (oxlint) + `npm test` (vitest, 18).

## Specs

- **S1** (verbatim) "Quiero que en animales, purtchases y payments se implemente cursor" — animals, purchases and payments list endpoints adopt keyset-cursor pagination following the existing animals mechanism (opaque token via `src/common/application/pagination/cursor.py`, `InvalidCursorError` → 422) and the users id-keyset repository pattern (JD2).
- **S2** (verbatim) "en usuarios y supplies me parece bien dejarlo con offset y limit ya que son listados que no tienen tantos registros" — users and supplies keep page/offset+limit contracts unchanged in pagination semantics.
- **S3** (verbatim) "Tambien se muestre el total de registros que hay segun la busqueda que se haga (Sin query params = numero total de registros, con query params = numero total de registros que coinciden)" — every surfaced list exposes `total` computed as a COUNT with the same filter conditions as the listing (no filters = all records), and the FE shows that counter over the table.
- **S4** (verbatim) "Los dropdowns deberian venir sin paginar" — dropdown/reference lists are never truncated by pagination.
- **S5** (verbatim) "normalilzar" los endpoints para los dropdowns (parametros), por ejemplo "/cattle/params/animal-type", "/finance/params/animal-supplies", "/finance/params/animal-supply-types" — dedicated reference endpoints (confirmed choice over `all=true`): scoped exactly like their sibling list endpoints (L4 evidence: type schemas have no tenant_id column → deployment-wide shared catalogs; supplies tenant-scoped), same role guards as siblings (router-level VIEWER), unpaginated, returning a light projection ({id, name} for types; {id, name, unit_of_measurement} for supplies).
- **S6** (verbatim) "deberia seguir los patrones de respuesta correspondientes que ya se definieron e implementan en otros endpoints del mismo estilo, recorda utilizar patrones, diseño, arquitectura, estructura, etc... que se implementan en cada proyecto" — backend follows the hexagonal layering (presentation router + dependency → application use case → domain port → persistence repository) and CursorPage envelope; web follows hooks + nuqs schemas + services/api zod-shaped types as established.
- **S7** (Scope accepted: "con respecto al alcance creo que si") — supplies list response wraps in a minimal `{items, total}` envelope staying offset/limit; web supplies hook limit raised to 100. Animals `total`/`has_next` must be correct in BOTH modes (offset first page included) and `next_cursor` emitted whenever `has_next && items`, decoupled from incoming cursor. Animals router `response_model` collapses to `CursorPage[AnimalSchema]` (drop dead union). Web types stop lying: `cursor`/`next_cursor` become `string | null`.
- **S8** (assumption) — payments list today has no FE consumer found; after cursor migration the FE consumer (if exists) navigates via `next_cursor`.
